루트 디렉토리에서 실행하라

가장 먼저 강조하는 것은 프로젝트 루트 디렉토리에서 클로드 코드를 실행하는 것이다. 클로드가 현재 디렉토리 기준으로 파일을 탐색하기 때문이다.

다른 곳에서 실행하면 프로젝트 구조를 읽어오는 데 어려움을 겪어 제대로 된 검색이나 플랜을 만들지 못할 수 있다. 예를 들어 apps 디렉토리 안의 api 디렉토리에서 실행하면 클로드는 api에 대한 프로젝트 구조밖에 읽지 못하고, 다른 곳으로 가려면 토큰을 많이 써야 해서 아주 비효율적이 된다.

CLAUDE.md는 왜 중요한가

/init이 중요한 이유는 CLAUDE.md 파일을 생성하기 때문이다. 이 파일이 프로젝트의 모든 컨텍스트를 담고 있는 하나의 파일이라는 것이다.

작동 원리를 이해해야 중요성이 보인다. 클로드는 모든 파일을 읽어올 수 있고, 읽은 뒤 플랜을 세우거나 태스크를 수행한다. 그런데 프로젝트가 크면 클수록 모든 것을 읽어야 해서 토큰 소모량이 커진다. 그래서 매번 파일을 읽어오는 비효율적인 방법 대신, CLAUDE.md에 프로젝트의 모든 구조를 정리해두고 클로드가 그 파일만 읽고 바로 태스크를 실행할 수 있게 만들어주는 것이다.

샘플 CLAUDE.md 구성을 이커머스 플랫폼 예시로 설명한다. 가장 위에는 절대 규칙, 즉 절대 하면 안 되는 것과 꼭 해야 하는 것을 써야 한다. “프로덕션 DB에 절대 쿼리하지 마라”, “환경변수 파일을 절대 커밋하지 마라” 같은 것들이다. 그다음 아키텍처를 트리 형식으로 설명하면 보기도 깔끔하고 클로드가 읽기도 깔끔하다. 이어서 테크 스택, 빌드·테스트 커맨드, 도메인 컨텍스트(상품의 색상·사이즈·재고 보유 같은 비즈니스 로직), 코딩 컨벤션(컴포넌트는 파스칼케이스, 유틸리티는 카멜케이스 등), 그리고 핵심 패턴(서버 컴포넌트를 기본으로 쓰고 클라이언트 상태가 필요할 때만 클라이언트 사용, API 에러는 AppError로 통일 등)이 들어간다.

다만 CLAUDE.md는 매번 읽어오기 때문에 커질수록 토큰 소모량이 커진다. 그래서 루트의 CLAUDE.md는 300줄 이내로 유지하는 것이 효율적이라고 말한다. 커지면 폴더별로 나누라는 것이다. 수파베이스 같은 데이터베이스는 데이터베이스용 CLAUDE.md를, API는 API용을, 웹 쪽은 웹용을 따로 생성해 루트 파일이 비대해지는 것을 방지한다. 이렇게 하면 클로드가 해당 영역을 작업할 때 훨씬 쉽고 가볍게 읽어 효율적으로 작동한다.

수정도 직접 할 필요가 없다. 프로젝트를 끝내고 코딩 컨벤션을 추가하고 싶다면 “방금 우리가 정한 패턴을 CLAUDE.md에 추가해 줘”라는 명령어만 입력하면 자동으로 업데이트된다.

트리거 키워드

CLAUDE.md에는 트리거 키워드를 등록할 수 있다. 커밋과 푸시하는 커맨드가 서너 개 있는데 이를 한 번에 실행하고 싶을 때 쓴다.

실제로 “어떤 작업이 끝나면 테스트를 돌리고 모두 패스한다는 가정하에 git commit과 git push를 해주는 키워드를 설정해 달라”고 요청하는 시연을 한다. 그 결과 “배포”라는 키워드가 감지되면 클로드가 네 번의 스텝을 거치게 된다. 테스트를 먼저 실행하고, 실패 시 보고하고 중단하며, 통과하면 git add 전부를 하고 커밋한 뒤 브랜치에 푸시하고 요약 결과를 출력하는 것이다. 이 네 스텝이 하나의 트리거로 등록된 셈이다.

컴파운드 엔지니어링

혼자가 아니라 팀으로 작업하는 프로젝트라면 CLAUDE.md를 푸시해 팀 전체가 공유하는 방법이 있다. 앤스로픽에서는 이것을 컴파운드 엔지니어링이라고 부른다고 소개한다. 말 그대로 팀 전체가 같은 규칙으로 클로드를 사용하는 것이다.

커밋 전에 로컬 전용 경로나 개인 API 키 같은 것은 빼야 한다. 팀이 CLAUDE.md를 관리하며 코딩 컨벤션과 아키텍처를 업데이트하면, 한 팀원이 아키텍처를 업데이트했더라도 다음에 같은 프로젝트를 풀했을 때 클로드가 이미 업데이트되어 있어 훨씬 효율적으로 활용할 수 있다.

단축키 (1) - Shift+Tab, 플랜 모드

핵심 단축키로 가장 먼저 꼽는 것이 Shift+Tab이다. 플랜 모드와 액셉트 에딧 모드를 전환한다.

차이는 클로드가 파일을 변경할 수 있는 쓰기 권한의 유무다. “테스트를 작성해 줘”라고 했을 때 액셉트 에딧 모드에서는 클로드가 바로 테스트 파일을 만들고 작성하기 시작한다. 반면 플랜 모드에서는 쓰기 권한이 없으니 말 그대로 플랜을 한다. 테스트를 어떻게 짜고 생성할지, 테스트의 구조와 유즈케이스가 무엇일지를 먼저 계획하고 검토받는 단계를 거친다. 그 플랜을 조정하거나 승인하면 그때 액셉트 에딧으로 바뀌어 실제로 만들고 실행한다.

플랜 모드를 써야 하는 실무적 이유를 정리한다. 첫째는 토큰 최적화다. 불필요한 코드 생성을 방지하기 때문이다. 바로 코딩해서 파일을 생성했는데 잘못됐다면 수정을 요청하고 재생성해야 하고, 두세 번만 반복돼도 토큰이 비효율적으로 많이 소모된다.

둘째는 컨텍스트 윈도우 관점이다. 플랜 모드로 플랜이 세워지면 그 플랜만 가지고 파일을 생성하니 훨씬 적은 컨텍스트로 작업할 수 있다. 반면 바로 파일을 생성하면 그 파일을 만들기 위해 탐색하는 과정의 모든 컨텍스트를 가진 상태에서 생성하게 되어, 이미 꽉 찬 상태에서 코딩하는 상황이 된다. 컨텍스트가 가득 찰수록 클로드 코드의 성능이 안 좋아진다는 것이다. 실행 정확도와 비용 관리 측면에서도 마찬가지이며, 앤스로픽에서도 플랜 모드로 먼저 시작하는 것을 추천한다고 전한다.

단축키 (2) - ESC, 스크린샷, iTerm 분할

ESC는 작업 중단이다. 작업 과정이 마음에 들지 않거나 잘못됐다고 판단되면 ESC를 눌러 “Interrupted”로 중단시킬 수 있다. 중단시키고 다른 인스트럭션을 주거나 아예 새 세션을 시작할 수 있다.

ESC를 두 번 누르면 이전 작업으로 돌아가는 리와인드 UI가 생성된다. 프롬프트를 여러 개 사용한 상태라면 맨 처음 프롬프트로 되돌아갈 수 있는 되감기 기능이다.

스크린샷은 터미널에 직접 드래그 앤 드롭할 수 있다. UI 작업을 할 때 원하는 UI/UX 톤을 말로 설명하는 것보다 이미지를 주는 것이 훨씬 정확하고 토큰 면에서도 효율적이라는 것이다. 프론트엔드 개발뿐 아니라 아키텍처도 머메이드 다이어그램 형태로 주면 클로드가 훨씬 효율적으로 파악하고 처리할 수 있으니, 아키텍처도 이미지 형태로 보관하고 읽게 하는 것을 추천한다.

iTerm 사용자를 위한 단축키도 알려준다. Cmd+D를 누르면 세로로 세션이 두 개 열리고, Cmd+Shift+D를 하면 가로로 창이 이등분된다. 창끼리 전환은 Cmd와 대괄호 표시로 좌우 이동이 가능하다.

가장 좋아하는 팁 - 느낌표로 배시 실행

강의자가 제일 좋아하는 팁이라고 소개하는 것은 클로드 코드 터미널 안에서 배시 명령을 실행하는 방법이다.

git status로 깃을 체크하거나 npm run build로 로컬 서버를 돌려야 할 때가 많은데, 이것을 몰랐을 때는 항상 다른 터미널을 열어 실행하고 닫는 식으로 했다고 한다. 그럴 필요가 없다. 느낌표를 붙이고 배시 커맨드를 실행하면 클로드 안에서 답변을 볼 수 있다는 것이다. !git status를 실행하면 고쳐진 파일들을 볼 수 있고, !npm run build를 하면 안에서 로컬 서버가 돌아가는 것을 볼 수 있다.

필수 슬래시 명령어

컨텍스트 관리부터 다룬다.

/context는 토큰량을 보여주는 커맨드다. 작업하다가 이것으로 토큰이 많이 쌓인 것 같다고 판단되면 조치를 취한다.

/clear는 대화 기록과 히스토리를 모두 정리해준다. 쌓여 있던 컨텍스트의 토큰을 모두 비워 프리 스페이스가 거의 다 비게 된다.

/compact는 대화 히스토리를 지우되 요약은 컨텍스트에 유지한다. 말 그대로 압축이다. 이 세션의 중요한 히스토리는 남기고 싶지만 컨텍스트는 정리하고 싶을 때 쓴다.

/model은 모델 선택이다. 세 가지가 있다. 오퍼스 4.6은 가장 똑똑하고 토큰을 가장 많이 쓰며 복잡한 작업에 좋다. 소넷은 오퍼스와 하이쿠의 중간으로, 테스트를 작성하는 것 같은 일상적 작업에는 큰 똑똑함이 필요 없으니 맡길 수 있다. 하이쿠는 가장 빠르고 토큰을 가장 적게 쓴다.

강의자 본인은 거의 오퍼스만 쓴다고 밝힌다. 소넷을 쓸 때는 병렬 작업을 할 때다. 4.6이 나오면서 에이전트 팀즈가 생겼는데, 서브에이전트를 사용할 때 아래 에이전트들에게 모두 오퍼스를 쓰게 하면 토큰이 진짜 빨리 닳아 없어지는 것이 눈으로 보인다는 것이다. 토큰은 총알 같은 것이라 다 써버리면 그다음 일을 할 수 없으니, 서브에이전트에게 일을 맡길 때는 소넷을 사용해 토큰을 아낀다.

/resume은 이전 세션으로 돌아가는 커맨드다. 실수로 세션을 닫았거나 컴퓨터가 꺼졌을 때 클로드를 실행한 뒤 이 커맨드로 원하는 대화로 돌아갈 수 있다. 클로드 밖에서는 claude --resume으로 같은 히스토리를 볼 수 있다.

/mcp는 지금 사용 중인 모든 MCP 서버를 보여준다. 강의자는 수파베이스 MCP와 노션 MCP를 쓰고 있다고 한다. MCP 서버가 많을수록 AI가 쓸 수 있는 도구가 많은 것이니 망치도 톱도 주는 셈이라 일을 더 잘할 수 있다.

그런데 여기가 양날의 검이라고 강조한다. MCP 서버는 컨텍스트를 차지하게 되어 있다. 아무것도 안 했는데도 컨텍스트를 보면 시스템 툴과 메모리 파일로 이미 8.4%가 사용되고 있는 것을 볼 수 있다는 것이다. MCP 서버가 클수록 차지하는 용량이 커져 비효율적인 관리가 된다. 그래서 많은 고수들이 MCP 사용을 자제하고, 특히 용량이 큰 MCP는 쓰지 말고 본인 니즈에 맞춰 커스텀 MCP를 만들어 쓰는 것을 추천한다고 전한다.

기타 명령어도 소개한다. /help는 클로드 코드에 대한 일반적인 것을 다 볼 수 있어 어떤 커맨드가 있는지 모를 때 유용하다. /config는 세팅을 보고 바꿀 수 있다. /export는 대화를 다른 세션으로 내보내는 커맨드로, 클로드에서 작업하다가 제미나이로 옮겨갈 때 컨텍스트를 가져갈 수 있다.

/output-style은 재미있는 커맨드다. 디폴트 외에 익스플래너토리는 왜 그렇게 했는지 설명해줘서 가르쳐주는 셈이고, 러닝(Learning)은 오히려 사용자에게 “이거 한번 해보라”고 시킨다. 클로드가 멈추고 사용자가 작은 코드를 작성하게 하는 것이다. 코딩을 배우고 싶거나 직접 손으로 짜보며 배우고 싶은 사람에게 2번이나 3번으로 설정해 배워보는 것도 좋겠다고 권한다.

커스텀 슬래시 명령어 만들기

마지막 데모는 나만의 커스텀 슬래시 명령어를 만드는 것이다. 앞서 CLAUDE.md에서 만든 트리거 키워드를 슬래시 커맨드로 만들 수 있다는 것이다.

“테스트를 하고 패스하면 git push를 하는” 반복 작업을 매번 쓰고 돌리는 것보다 한 큐에 끝내는 것이 효율적이니 만들어달라고 요청한다. 그러면 .claude 폴더 안에 commands라는 폴더가 새로 만들어지고 그 안에 .md 파일이 생성된다.

파일을 열어보면 디스크립션에 “테스트 실행 후 커밋 푸시”가 있고, 아래 워크플로우 순서대로 테스트 먼저 실행, 실패 시 중단, 통과 시 커밋하고 푸시, 결과 출력이 적혀 있다. 앞서 본 트리거 키워드와 같은 내용을 슬래시 커맨드로 만든 것이다. 파일 이름대로 명령어를 쓰면 되는데, 클로드 세션을 끄고 다시 들어와야 인식된다.

트리거 키워드와 슬래시 커맨드의 차이도 설명한다. 비슷하지만 슬래시 명령어는 탭 자동완성이 되고, 더 중요하게는 클로드 코드가 구조적으로 인식하기 때문에 훨씬 안정적이라는 것이다. 슬래시 커맨드는 클로드 코드의 아키텍처·인프라의 일부이므로 리뷰나 배포 같은 반복 작업을 여러 개로 모듈화하면 생산성 향상에 훨씬 도움이 된다.

2부 실전편 - 컨텍스트 관리와 워크플로우

왜 대화가 길어지면 클로드가 멍청해지나

2부는 문제 제기로 시작한다. 클로드 코드 기본은 아는데 왜 남들만큼 효과를 못 보는가. 대화가 길어지면 클로드가 점점 멍청해지고, 같은 실수를 반복하고, 코드를 수정하다가 오히려 다른 곳이 망가지는 경험이 있지 않느냐는 것이다. 이런 문제 대부분은 컨텍스트 관리와 워크플로우의 문제라고 진단한다.

“클로드 코드에서 컨텍스트는 왕”이라는 것이 핵심 명제다. 컨텍스트를 어떻게 관리하느냐에 따라 답변 품질이 천차만별로 달라진다는 것이다.

세컨드 브레인과 /memory

강력한 패턴으로 세컨드 브레인 구축을 제시한다. 클로드와 작업하며 배운 것들, 새로운 패턴, 해결책, 의사결정 이유 같은 것을 로컬 마크다운 파일에 저장하는 것이다.

실제로 쓰고 있는 파일을 보여주는데, “프로젝트의 주요 결정을 기록한 문서”이며 “세컨드 브레인으로 활용하여 과거 결정의 맥락과 근거를 빠르게 참조할 수 있도록 함”이라고 적혀 있다. 앱을 개발하며 마주했던 패턴과 해결책, 의사결정 이유를 목차별로 정리해둔 파일이다. 다음에 비슷한 작업을 할 때 클로드에게 이 파일을 읽히면 된다.

그런데 이제는 수동으로 관리할 필요가 없어졌다고 한다. 클로드 코드가 /memory라는 자동 메모리 시스템을 최근 릴리즈했기 때문이다. 클로드가 작업하며 자동으로 학습한 내용을 memory.md 파일에 저장하며, 빌드 명령·디버깅 인사이트·코드 패턴 같은 것을 알아서 기억한다. 매 세션 시작 시 이 파일이 자동 로드되어 이전 세션의 지식을 활용할 수 있다. 그냥 “기억해 줘”라고 말하면 저장되고 /memory 명령으로 확인하거나 편집할 수 있다.

다만 수동 방식도 여전히 유효하다고 덧붙인다. 특히 팀원과 공유해야 하는 컨텍스트는 명시적으로 작성하는 것이 좋으니, 개인 메모리는 /memory, 팀 공유 지식은 CLAUDE.md로 나눠 쓰는 것을 추천한다.

레이지 로딩 - “전부 떠먹이지 말고 검색하게 하라”

다음 질문은 이 컨텍스트를 언제 어떻게 불러올 것인가다. 여기서 레이지 로딩이 쓰인다.

흔한 실수는 API 스펙, DB 스키마, 코딩 컨벤션, 아키텍처 문서를 전부 CLAUDE.md 하나에 몰아넣는 것이다. 문제는 CLAUDE.md가 매 세션마다 자동 로드된다는 점이다. 거기에 API 엔드포인트 50개, DB 테이블 스키마 40개가 들어 있다면 매번 수천 토큰이 날아가는데 정작 작업에 필요한 건 그중 5%도 안 된다.

핵심은 CLAUDE.md에는 규칙과 참조만 두고 상세 내용은 별도 파일로 분리하는 것이다. 나쁜 예는 CLAUDE.md가 API 엔드포인트 50개를 모두 갖고 있는 것이고, 좋은 예는 참조만 보여주는 것이다. 강의자의 CLAUDE.md는 맨 마지막에 참조 섹션이 있고 참조할 마크다운 파일의 경로를 알려준다.

이 전략을 쓰면 레이지 로딩이 되어 클로드가 필요할 때만 해당 파일을 읽는다. “DB 스키마 업데이트해 줘”라고 하면 CLAUDE.md에서 db-schema.md 파일만 읽고 작업을 수행하며, 다른 API 스펙이나 프론트엔드 아키텍처 파일은 로드하지 않는다.

루트 CLAUDE.md가 커지는 것이 걱정된다면 폴더별로 따로 만들면 된다. apps/api 아래에 API 관련 CLAUDE.md, web 아래에 웹 관련, supabase에 데이터베이스 관련을 따로 만들어 관리하면 그 폴더의 파일을 작업할 때 그 폴더의 CLAUDE.md만 읽기 때문에 루트의 비대화를 막으면서 컨텍스트 낭비도 방지한다.

결국 핵심은 전부 떠먹이는 것이 아니라 필요한 것만 검색해서 가져오게 하는 것이다.

한 세션 한 기능 - 가장 실용적인 규칙

컨텍스트 윈도우 200k 토큰은 많아 보이지만 실제로 쓰다 보면 금방 찬다. /clear와 /context 명령어가 있지만, 코딩하다가 일일이 컨텍스트가 얼마나 찼는지 체크하고 컴팩트하는 것은 현실적이지 않다고 인정한다.

그래서 가장 실용적인 규칙은 “한 세션에서는 한 피처, 한 작업만 하자”이다. 하나의 세션에서 여러 기능을 연달아 구현하는 습관을 들이지 말라는 것이다. 로그인 기능 구현이 끝났다면 /clear를 하거나 아예 새 세션을 시작하고 다음 기능으로 넘어가라고 권한다.

이것이 중요한 이유는 작업을 세분화하는 습관과 직결되기 때문이다. “결제 시스템 전체 만들어 줘”가 아니라 “스트라이프 웹훅 핸들러 구현해 줘” 같은 단위로 쪼개야 한다는 것이다.

실전 워크플로우는 이렇다. ①플랜 모드에서 전체 작업을 설계하고 단계를 나눈다. ②/clear 또는 새 세션을 연다. ③플랜의 첫 번째 단계만 구현한다(이때 멀티 터미널로 하나씩 맡기는 것을 추천하며, 더 나아가면 서브에이전트와 에이전트 팀즈까지 쓸 줄 알아야 한다). ④완료되면 다시 /clear하고 다음 단계로 넘어간다.

핵심 원칙은 “신선한 컨텍스트가 부풀어진 컨텍스트보다 낫다”이다. 이전 대화에 집착하지 말고 매 작업마다 깨끗한 세션으로 시작하는 것이 오히려 더 좋은 결과를 만든다는 것이다.

MCP 관리와 머메이드 다이어그램

MCP를 여러 개 연결하면 도구 설명만으로 토큰을 크게 소비한다. 그래서 /mcp로 현재 가진 MCP를 확인하고 지금 작업에 안 쓰는 MCP는 비활성화할 줄 알아야 한다. 노션을 쓰지 않는다면 disable을 누르면 된다.

특히 노션이나 리니어 같은 MCP는 도구 설명이 매우 커서 토큰을 크게 잡아먹는다. 이런 경우 통째로 붙이지 말고 자주 쓰는 기능만 추려 직접 래핑하라고 조언한다. 필요한 엔드포인트만 감싸면 토큰 절약은 물론 응답 품질도 올라간다는 것이다.

머메이드 다이어그램으로 아키텍처를 정리하는 방법도 소개한다. A→B 형식으로 인증 서비스, 주문 서비스, 결제 서비스, 재고 서비스를 표현하면 클로드가 훨씬 빠르게 이해하고 컨텍스트도 효율적으로 저장할 수 있다는 것이다. 매번 시스템 구조를 말로 설명하지 말고 docs/architecture.md 같은 파일에 기능별로 정리해두고 레이지 로딩으로 참조하게 하라고 권한다.

무거운 작업은 스크립트로 오프로드

무거운 데이터 처리를 대화 안에서 시키면 컨텍스트가 오염될 수밖에 없다. 큰 파일을 읽고 처리하는 과정에서 출력이 너무 길어지기 때문이다.

구체적 예시로 데이터베이스 마이그레이션을 든다. 10만 행짜리 CSV를 파싱해야 하는데, 클로드가 그것을 읽고 모두 컨텍스트에 저장하고 처리하는 과정에서 컨텍스트가 오염되고 품질이 낮아진다는 것이다.

대신 클로드에게 CSV를 파싱하는 DB 마이그레이션 스크립트를 작성해달라고 하고, 그 스크립트를 돌려서 나온 JSON 같은 출력만 받아 다음 작업을 진행하게 한다. 이렇게 하면 클로드가 큰 파일을 읽을 필요도 데이터 처리를 할 필요도 없이 결과값만 받아 작업하니 컨텍스트가 깨끗하게 유지된다.

워크플로우 (1) - 플랜 모드의 중요성

클로드 코드를 잘 쓰는 사람들의 공통점은 명령어만 아는 것이 아니라 어떤 워크플로우와 철학으로 쓰는가, 어떤 모델을 쓰는가가 다르다는 것이다. 그중 모두가 공통적으로 말하는 것이 플랜 모드의 중요성이다.

큰 변경 작업뿐 아니라 어떤 작업을 시작할 때도 반드시 플랜 모드로 시작하라고 권한다. 순서는 플랜 모드에서 작업을 설명하고, 클로드가 계획을 제시하고(어떤 파일을 수정하고 어떤 접근을 할지), 그것을 리뷰하고 피드백을 주고, 다른 옵션을 요청해 비교해보고, 만족스러운 계획이 나오면 액셉트 모드로 바꿔 실행하는 것이다.

플랜 없이 바로 실행하면 클로드가 엉뚱한 방향으로 코드를 대량 수정해버리는 참사가 발생할 수 있고 컨텍스트도 낭비되며, 사용량 제한이 있는 상황에서 시간과 리소스를 낭비하는 결과가 된다.

워크플로우 (2) - TDD와 씽킹 읽기

TDD 기반 스마트 코딩을 두 번째로 든다. 작은 변경을 했다면 바로 다음 변경으로 넘어가지 말고 테스트를 작성해 잘 돌아가는지 확인하고 커밋하는 것을 반복하라는 것이다. 문제가 생겨도 마지막 커밋으로 돌아가면 되니 디버깅이 훨씬 쉬워진다. 이것을 습관화하지 않으면 AI가 수많은 변경을 만드는데 내가 작성한 것이 아니라 꼼꼼히 다 보지 못하니 나중에 디버깅이 진짜 힘들어진다는 경고다.

세 번째는 씽킹 읽기다. 클로드가 생각하는 과정을 보여주는데 이것을 무시하면 안 된다는 것이다. “이 함수는 X를 하는 것 같으니 이걸 하겠다”며 가정을 세우는 순간이 있는데 그 가정이 틀릴 때가 있다. 그 순간 ESC로 바로 중단시키고 다시 시작하거나 가정을 수정해줘야 한다. 잘못된 가정 위에 쌓은 코드는 전부 쓸모없으니 초반에 잡는 것이 핵심이라고 강조한다.

워크플로우 (3) - 다른 AI에게 비평받기

유용하게 쓰는 팁으로 다른 AI에게 비평을 받는 방법을 소개한다. 클로드와 작업하다가 클로드의 플랜을 다른 AI는 어떻게 생각할지 궁금했다는 것이다.

플랜을 익스포트해 챗GPT나 제미나이에게 보여주며 “이 대화를 분석해서 클로드가 놓치고 있는 것이나 잘못된 접근이 있으면 지적해 줘”라고 하면, 각 AI 모델이 정말 다른 시선으로 바라보고 다른 문제를 정의하고 다른 솔루션을 제시하는 것을 볼 수 있다고 한다. 그 피드백으로 새로운 접근법이 나올 수도 있다.

여기서 팁은 이 과정을 커스텀 스킬로 자동화할 수 있다는 것이다. 한 AI 모델의 플랜을 다른 AI에게 전달해 취합하고 요약을 보여주는 스킬을 만들면 모든 작업이 자동화된다.

워크플로우 (4) - 에러 로그는 통째로

다섯 번째 팁은 에러 로그를 그대로 붙여 넣으라는 것이다. 에러를 해석해서 설명하지 말고 통째로 던지는 것이 가장 좋다. 우리가 해석하면 정보를 빠뜨리거나 잘못된 정보를 줄 수 있는데, 클로드는 스택 트레이스 분석에 아주 유능한 모델이므로 그대로 주면 제일 일을 잘한다는 것이다.

워크플로우 (5) - TODO 파일

TODO 파일을 프로젝트 시작부터 끝까지 하나의 파일에서 관리하라고 권한다. AI는 오늘 할 일, 내일 할 일을 우리처럼 알고 있는 게 아니기 때문에, TODO 파일을 계속 관리하며 한 것과 안 한 것을 공유해주면 AI도 작업 현황을 알 수 있다는 것이다.

실전 워크플로우는 오늘 할 일(결제 구현, 랜딩 페이지 다듬기, 구독 시스템, 버그 수정 등)을 정리해 todo.md에 체크리스트로 작성하고, 클로드에게 “todo.md부터 시작해 줘”라고 지시한 뒤, 에이전트 팀즈로 여러 태스크를 병렬 처리하고, 세션 종료 시 “todo.md에 업데이트해 줘”라고 말하면 진행 상황이 자동 반영되는 것이다. 이렇게 하면 여러 세션에 걸쳐 작업의 연속성을 유지할 수 있다.

WAT 프레임워크

마지막으로 WAT라는 프로젝트 관리 방법론을 소개한다. 네이트 B 존스라는 유튜버가 제안한 것으로 나쁘지 않아 몇 번 써봤다고 한다. W는 Workflow, A는 Agent, T는 Tools다.

Workflow의 핵심은 평이한 영어로 작업 흐름을 명확하게 정의하는 것이다. 코드를 쓰기 전에 이 작업이 어떤 단계로 이루어져야 하는지를 글로 적는다. 투두 앱에 마감일 알림 기능을 추가한다면 플랜 모드에서 “①DB 스키마에 due_date와 notification_sent 컬럼 추가 ②마감일 설정 UI 컴포넌트 구현” 식으로 각 단계마다 테스트 작성 후 통과 확인까지 명시하는 것이다. 이렇게 하면 삽질을 줄이고 클로드가 방향을 잃고 헤매는 경우를 줄일 수 있다.

Agent에서는 셀프 힐링 메커니즘이 중요하다. 에러가 나면 스스로 로그를 읽고 원인을 파악하고 코드를 수정하고 다시 실행하는 루프가 자동으로 돈다는 것이다. 그리고 서브에이전트로 역할을 분리해 병렬 처리하면 10분 걸릴 작업을 세 개의 서브에이전트로 3～4분에 끝낼 수 있다.

Tools는 거대한 스크립트보다 작은 단위의 스크립트 여러 개가 훨씬 낫다는 뜻이다. 클로드가 스크립트 실행 중 실패했을 때 큰 스크립트 하나보다 작은 스크립트 하나를 돌리고 디버깅하는 것이 훨씬 효율적이기 때문이다. 실전 도구로는 배시 스크립트, MCP 서버, 훅스가 있다.

블로그 댓글 기능 추가를 예시로 적용해 보여준다. 워크플로우로 “댓글 테이블 스키마 설계 및 마이그레이션”부터 “각 단계마다 테스트 작성 및 통과 확인”까지 순서를 정의하고, 클로드가 코디네이터로서 에이전트들에게 작업을 분배해 API 구현 동안 다른 서브에이전트가 테스트를 미리 설계하고 에러가 나면 셀프 힐링으로 복구하며, 도구로 migrate.sh 스크립트와 MCP 깃허브 PR 생성, 훅으로 커밋마다 테스트 자동 실행을 붙이는 것이다.

이 프레임워크의 핵심은 AI의 추론과 코드 실행을 분리하는 것이다. 클로드에게 생각하게 하고 실행은 별도 도구나 스크립트에 맡기면 복잡한 워크플로우도 안정적으로 관리할 수 있다는 것이다.

3부 심화편 - 스킬, 서브에이전트, 훅스

스킬이란 - “AI에게 주는 업무 매뉴얼”

스킬을 한마디로 정의하면 AI에게 주는 업무 매뉴얼이다.

회사에 신입 사원이 들어왔을 때 매번 “이건 이렇게 해, 저건 저렇게 해” 말로 지시하면 시키는 사람도 힘들고 결과물도 들쭉날쭉하다. 그래서 업무 매뉴얼을 만든다. 한번 만들어두면 누가 하든 일정한 품질이 나오기 때문이다. 클로드 스킬이 바로 이 역할을 한다. SKILL.md 파일 하나에 어떤 순서로 할지, 어떤 형식으로 만들지, 뭘 확인할지를 적어두면 클로드가 그대로 따라서 매번 같은 품질로 결과를 만들어준다.

클로드 코드의 스킬은 에이전트 스킬즈라는 공개 표준을 따르므로 클로드 코드에서만 쓸 수 있는 것이 아니라 다른 AI 도구에서도 쓸 수 있는 범용 규격이라는 점도 짚는다.

프롬프트와 스킬의 차이도 정리한다. 재사용성 면에서 프롬프트는 매번 처음부터 입력하거나 복사·붙여넣기를 해야 하지만 스킬은 한 번 만들면 자동으로 트리거된다. 일관성 면에서 프롬프트는 같은 요청이어도 결과가 매번 다른데, 이는 에이전트의 장점이자 단점이다. 같은 요청에 같은 아웃풋이 필요한 경우 스킬은 포맷과 체크리스트로 품질을 강제할 수 있다. 확장 면에서 프롬프트는 텍스트 덩어리로 확장해야 하지만 스킬은 참조 문서, 스크립트, 서브에이전트를 자체에서 실행할 수 있다. 정리하면 프롬프트가 한 번의 지시라면 스킬은 재사용 가능한 업무 시스템이다.

스킬을 써야 하는 세 가지 이유는 반복 작업 자동화, 결과물 품질의 일정함, 팀 공유 가능이다. PPT를 만들 때마다 “이 주제로, 이 디자인으로, 이 색상으로, 이 형식으로”를 매번 길게 입력했다면 스킬을 만들 때이며, 한번 만들어두면 /ppt만 치면 끝이고 자동 트리거를 설정하면 “발표 자료 만들어 줘”라고만 말해도 실행된다는 것이다.

스킬의 진짜 핵심 - 2단계 로딩

스킬은 디렉토리 단위로 관리된다. SKILL.md가 진입점이고 필요에 따라 sample.md나 generate.py 같은 지원 파일을 함께 둔다. 구조는 이게 전부다.

그런데 이 단순한 구조 뒤에 숨어 있는 로딩 방식이 진짜 핵심이라고 강조한다. 솔직히 클로드 코드의 진짜 힘은 CLAUDE.md가 아니라 이 스킬 시스템에서 나온다는 것이다.

이유는 컨텍스트 윈도우가 한정되어 있기 때문이다. 아무리 좋은 규칙을 만들어도 컨텍스트가 꽉 차버리면 AI가 앞에서 뭘 했는지 잊어버리고 품질이 나쁜 코드가 나온다. 스킬은 필요할 때만 불러오고 쓰고 나면 알아서 치워주기 때문에 이 문제를 깔끔하게 해결한다.

스킬은 두 단계로 나눠 불러온다. 첫 번째 단계는 디스크립션으로, 스킬 이름과 한 줄 설명만 아주 작은 컨텍스트를 차지한다. 두 번째 단계인 전체 프롬프트는 필요할 때만 온디맨드로 로딩된다. 평소에는 이름과 설명만 올라가 있다가 스킬이 호출될 때 클로드의 판단하에 전체 내용을 불러오고, 참고 파일도 필요한 시점에 읽는다.

CLAUDE.md와 비교하면 확실해진다. CLAUDE.md는 세션 시작할 때마다 항상 자동 로딩되어 매번 컨텍스트를 차지한다. 반면 스킬은 이름과 디스크립션만 짧게 들어가므로 스킬당 50～100바이트 수준이며, 전체 내용이 50KB라도 실제로 쓸 때만 불러온다. 정리하면 CLAUDE.md에는 항상 지켜야 할 핵심 규칙만 넣고 가끔 쓰는 참고 자료나 반복 작업은 스킬로 분리하는 것이 좋다.

스킬 vs MCP vs 서브에이전트

컨텍스트 효율 관점에서 셋을 비교한다.

MCP는 스킬과 완전히 다르다. MCP 서버를 연결하면 거기 있는 모든 도구의 설명이 시작할 때부터 올라가고 세션마다 계속 포함된다. 도구가 10개면 10개 전부, 50개면 50개 전부이며 안 써도 그렇다. 그래서 MCP 서버를 많이 연결할수록 컨텍스트 부담이 커진다. 같은 기능이라면 MCP보다 스킬이 훨씬 가벼우니, 간단한 작업이라면 MCP 대신 로컬 스크립트를 스킬로 감싸는 것을 추천한다.

서브에이전트는 재미있는 경우다. 실행 중에는 가장 효율적인데, 별도의 컨텍스트를 사용하고 그 공간에서 돌아가기 때문이다. 서브에이전트가 파일 100개를 뒤져도 그 결과는 서브에이전트 컨텍스트에만 있고 메인 컨텍스트에는 요약된 결과만 돌아온다.

그러나 함정이 있다. 에이전트의 이름, 도구, 시스템 프롬프트 같은 설명은 시작할 때부터 로드되어 있어 MCP와 비슷하다는 것이다. 에이전트 10개를 만들어두면 안 쓴 에이전트도 매번 컨텍스트를 차지한다. 반면 스킬은 설명이 50～100바이트 수준이라 20개를 만들어도 부담이 거의 없다.

정리하면 안 쓸 때 가장 가벼운 것은 스킬이고, 실행 중에 가장 효율적인 것은 서브에이전트다. “뭐가 제일 좋아”가 아니라 언제 공간을 아끼고 싶은지에 따라 선택이 달라지므로 상황에 맞게 섞어 쓰는 것이 핵심이다.

디스크립션이 품질을 좌우한다

SKILL.md는 윗부분의 설정 정보(이름, 디스크립션)와 아랫부분의 본문(프롬프트)으로 구성된다.

디스크립션은 클로드가 “이 요청에 이 스킬이 맞겠다”고 스스로 판단하는 핵심 필드이므로 품질이 매우 중요하다. 클로드는 단순히 단어가 같은지 비교하는 게 아니라 디스크립션을 읽고 판단하기 때문에, 사용자가 실제로 쓸 법한 말(PPT 만들어 줘, 슬라이드 제작 같은 표현)을 넣어줘야 자동으로 잘 작동한다.

나쁜 예는 “문서를 생성하는 스킬”처럼 추상적인 것으로, 클로드가 언제 어떻게 사용할지 판단이 불가능하다. 좋은 예는 “PPT 발표자료 자동 생성. PPT 만들어 줘. 발표자료 작성. 슬라이드 제작”처럼 핵심 기능과 트리거 표현을 세 개 이상 포함하는 것이다. 작성 팁은 핵심 기능이 첫 문장에 나오는가, 사용자가 실제로 말할 법한 표현이 세 개 이상인가, 비슷한 다른 스킬과 구별되는가이다.

스킬 만들기 실습 - skill-creator

스킬을 만드는 방법은 둘인데 수동으로 SKILL.md를 작성하는 것은 추천하지 않는다. 클로드에 내장된 skill-creator 플러그인이 있기 때문이다. “스킬 만들어 줘”라고 말하는 순간 이것이 자동 트리거되는데, 이 자체가 스킬 자동 트리거를 보여주는 좋은 예시이기도 하다.

설치는 /plugin으로 플러그인 마켓플레이스에 들어가 cloud plugins official에서 browse plugins로 skill-creator를 검색해 인스톨한다.

그다음 준비한 프롬프트를 붙여넣는다. “PPT 발표자료를 자동 생성하는 스킬을 만들어 줘. 발표 주제, 청중, 발표 시간을 입력하면 슬라이드 구성이 나와야 해. 슬라이드의 제목, 핵심 메시지, 시각 자료, 지시 사항 포함. 아웃풋은 PPTX 파일로 생성, 자체 검증 체크리스트 포함.” 그러면 skill-creator가 자동 트리거되어 스킬이 생성된다.

테스트도 시연한다. /clear 후 “PPT 생성해 줘. 2026년에 클로드 코드를 사용해야 하는 이유. 청중은 클로드 코드를 접해보지 못했거나 잘 모르는 사람들. 길이는 30분”이라고 입력하니 스킬이 성공적으로 트리거된다. python-pptx 라이브러리를 불러 슬라이드를 기획하는 것을 보여준다.

기다리는 동안 SKILL.md 파일을 함께 본다. 이름과 디스크립션만 컨텍스트에 로드되고 그 아래가 실질적인 프롬프트다. 워크플로우로 스텝 1 입력 수집, 스텝 2 슬라이드 기획, 표준 슬라이드 구조, 슬라이드 유형별 활용, 슬라이드별 콘텐츠 작성 필수 요소, 작성 원칙, 청중 맞춤 조정, 그리고 생성 단계(16:9 비율, 주제에 맞는 컬러 팔레트, 폰트 페어링, 레이아웃 변화, 스피커 노트, 파일명 규칙), 마지막으로 검증 체크리스트(슬라이드 수가 발표 시간에 적절한가 등)가 들어 있다.

결과물은 “2026년 클로드 코드를 사용해야 하는 이유”부터 핵심 세 가지와 Q&A까지 PPT가 잘 만들어진 것을 보여준다. 첫 시도치고 꽤 괜찮지 않느냐며, 이것을 계속 갈고닦아 자신의 톤앤매너와 브랜딩 컬러를 입히면 말 한마디로 내 슬라이드를 생성할 수 있는 시대에 와 있다고 말한다. 처음부터 완벽할 필요 없이 쓰면서 점진적으로 정교하게 만들어가라고 권한다.

스킬의 미래에 대한 전망도 덧붙인다. 스킬은 결국 앱스토어에서 다운로드받는 앱처럼 될 것이며, 사람들에게 공유하고 나중에는 사고파는 시대가 올 것이라는 것이다.

저장 위치에 따라 사용 범위가 달라진다. 프로젝트에서만 쓰려면 프로젝트 폴더에, 모든 프로젝트에서 쓰려면 홈 디렉토리의 skills 폴더에, 조직 전체에서 공유하려면 플러그인으로 배포한다. 클로드 코드가 제공하는 번들 스킬도 있는데, simplify 같은 것은 코드 품질을 자동으로 검토해준다.

서브에이전트

서브에이전트는 메인 클로드 안에서 별도의 작업 공간, 별도의 컨텍스트를 가진 도우미를 하나 더 생성하는 것이다. 각 서브에이전트는 자기만의 지시사항, 쓸 수 있는 도구, 별도 권한을 갖는다.

필요한 이유는 메인에서 파일 100개를 뒤지면 그 결과가 전부 쌓여 공간을 차지하기 때문이다. 서브에이전트에게 맡기면 조사 결과는 서브에이전트 컨텍스트에만 남고 메인은 오염되지 않으며 요약만 돌아온다.

핵심 장점 네 가지는 병렬 처리(여러 작업을 동시에 실행해 전체 소요 시간 단축), 컨텍스트 보호, 전문화(테스트 서브에이전트, 프론트엔드 서브에이전트, 백엔드 서브에이전트처럼 역할 부여), 재사용(여러 워크플로우에서 활용하고 팀과 공유)이다.

하면 좋은 것과 안 되는 것도 구분한다. 독립적인 작업을 병렬로 분배하는 것은 좋지만 의존성 있는 작업을 무리하게 병렬화하는 것은 추천하지 않는다. 명확한 역할과 범위를 지정해야 하며, 하나의 서브에이전트에게 테스트도 DB 마이그레이션도 프론트·백엔드 작성도 모두 시키는 것은 전문화가 떨어져 추천하지 않는다. 서브에이전트가 반환한 결과는 메인에서 통합 처리하는 것이 좋고, 에러 발생 시 전체 프로세스가 멈추지 않게 대비책을 마련해야 하며, 결과 검증 없이 그대로 쓰는 것은 추천하지 않는다.

내장 서브에이전트

클로드 코드도 내부적으로 내장 서브에이전트를 활용하고 있다는 점을 밝힌다.

Explore 에이전트는 코드 탐색, 파일 검색, 구조 파악에 특화되어 코드베이스 이해가 필요할 때 자동 트리거되며 빠르고 저렴한 하이쿠 모델을 사용한다. Plan 에이전트는 계획 수립에 특화되어 있다. General-purpose 에이전트는 다단계 작업에, Bash 에이전트는 별도 세션에서 터미널 명령 실행에 쓰인다. Claude Code Guide 에이전트는 클로드 코드 기능에 대한 질문에 답한다.

Explore 에이전트가 하이쿠를 쓰는 것이 핵심이라고 짚는다. 서브에이전트 모델로 오퍼스를 쓰는 것은 추천하지 않으며, 소넷이나 하이쿠로 병렬 처리해 컨텍스트를 효율적으로 관리하고 토큰 소비를 줄이라는 것이다.

커스텀 에이전트 만들기 실습

/agents 명령어로 커스텀 에이전트를 만드는 과정을 시연한다.

명령어를 치면 “Create new agent”가 나오고, 프로젝트 레벨과 개인 레벨 중 선택하고(프로젝트 레벨 선택), “Generate with Claude”(추천)를 고른다. 그리고 에이전트가 무엇을 하고 언제 사용되어야 할지를 쓴다. 준비한 프롬프트는 “너는 유닛 테스트 생성 에이전트야. 기존 테스트 프레임워크를 감지해서 사용하고, 테스트는 독립적이고 결정적으로 유지하고, 네이밍 컨벤션에 따라 생성해 줘”다.

다음은 툴 선택이다. 모든 권한을 줄지, 읽기만 가능하게 할지(플랜 에이전트 같은 경우), 수정이나 실행이 가능하게 할지, MCP 툴을 쓸 수 있게 할지를 고른다. 그다음 모델을 고르는데 소넷이 이미 디폴트로 되어 있다. 이는 클로드가 서브에이전트에 소넷을 추천한다는 뜻이라고 해석한다. 색깔도 선택하는데, 서브에이전트가 다양할 때 빠르게 구분하기 위한 것이다.

에이전트 메모리를 활성화할지도 묻는데 추천이라고 되어 있다. 에이전트가 자신의 로컬 메모리를 계속 업데이트하며 셀프 러닝을 할 수 있게 만드는 메커니즘이라 아주 중요하니 꼭 활성화하라고 권한다.

생성된 에이전트를 실제로 써본다. 테스트 관련 작업은 메인 에이전트에서 돌릴 필요가 없으며, 파일에 대한 모든 컨텍스트를 메인에 담을 필요가 없으니 테스트는 무조건 서브에이전트를 쓰는 것을 추천한다는 것이다. 실행하니 DB 관련 코드 중 테스트가 없는 파일 두 개를 발견해 에이전트를 트리거하고, 에이전트 컨텍스트 안에서 테스트를 모두 생성한 뒤 통과까지 확인한다.

에이전트도 스킬처럼 한번 만들고 끝이 아니라 계속 점진적으로 개선하는 것이 좋고, 팀끼리 공유가 가능하니 좋은 에이전트를 만들어 팀에서 함께 개선하며 쓰는 것이 미래가 될 것이라고 전망한다.

저장 위치는 홈 디렉토리의 agents 폴더면 개인용, 프로젝트의 agents 폴더면 팀과 공유하는 프로젝트 전용이다. 후자는 깃에 푸시하고 팀원이 풀해서 쓸 수 있다. 한편 에이전트를 여러 개 만들면 정의가 모두 컨텍스트에 로드되어 효율이 떨어지므로, CLI에서 즉석으로 만들면 생성되고 사라져 컨텍스트를 효율적으로 쓸 수 있으며 CI/CD 같은 일회성 작업에 유용하다고 덧붙인다.

서브에이전트 활용 패턴

네 가지 패턴을 제시한다. 격리 패턴은 별도 컨텍스트에서 작업을 수행하고 메인에 결과만 반환하는 것이다. 병렬 패턴은 여러 에이전트를 동시에 실행해 속도를 극대화한다. 체인 패턴은 한 에이전트의 결과를 다음에 전달해 순차 처리하는 것으로, 분석 에이전트 → 리팩터 에이전트 → 테스트 에이전트 → 리뷰 에이전트 식이다. 마지막은 재귀 패턴이다.

서브에이전트를 쓸지 메인을 쓸지는 “직접 할 것이냐 심부름을 시킬 것이냐”로 비유한다. 간단한 건 직접 하는 게 빠르지만, 시간이 오래 걸리는 일을 직접 하면 그동안 다른 걸 못 하니 심부름을 시키고 결과만 받는 게 낫다는 것이다.

메인 대화가 좋은 경우는 바로바로 대화하며 하는 단일 스레드 순차 처리, 모든 컨텍스트를 공유해야 하는 일, 순서대로 실행해야 하는 일이다. 판단 기준은 두 가지다. 작업이 독립적인가, 그렇다면 서브에이전트를 쓴다. 컨텍스트 오염이 우려되는가, 그렇다면 서브에이전트로 격리한다.

에이전트 팀즈

서브에이전트를 넘어서는 기능으로 에이전트 팀즈를 소개한다. 여러 클로드 코드 인스턴스가 팀으로 협업하는 기능이다.

서브에이전트와의 차이는 리더 에이전트가 작업을 조율하고 팀원에게 분배하며, 팀원끼리 직접 메시지를 주고받을 수 있다는 점이다. 서브에이전트는 메인 세션하고만 소통할 수 있고 에이전트끼리는 소통이 불가능하다. 에이전트 팀즈는 각 팀원이 독립적인 컨텍스트를 가지면서도 서로 협력하는 패턴으로, 마치 실제 개발팀처럼 프론트엔드 담당, 백엔드 담당, 테스트 담당이 동시에 작업하며 필요할 때 소통하는 구조다. 이 기능이 에이전틱 엔지니어링의 진짜 중요한 기능이라고 평가한다.

훅스 - 클로드 코드의 자동화 엔진

훅스는 클로드 코드의 자동화 엔진이다. 흐름은 이벤트 발생 → 훅 감지 → 액션 실행이다. 파일 저장이나 도구 호출, 알림 수신 같은 이벤트가 발생하면 매처가 조건을 검사하고, 조건이 맞으면 린트 실행이나 포맷 적용, 알림 전송 같은 액션이 자동 실행된다.

/hooks로 현재 설정된 훅 목록을 확인할 수 있다. 데모로 클로드가 응답 대기 상태에 들어갈 때마다 macOS 알림과 효과음을 보내주는 훅을 만든다. 훅을 추가하려면 settings.json을 직접 편집하거나 클로드에게 말하면 되는데, 클로드를 쓰는 것이 제일 좋다고 한다. “클로드가 응답 대기 상태에 들어가면 macOS 알림과 효과음이 나오는 훅을 만들어 줘”라고 하니 훅이 설정되고 실제로 알림이 온다.

생성된 파일을 보면 Stop 이벤트에 스크립트가 등록되어 있고, “응답이 완료되었습니다”라는 타이틀과 Glass 사운드, 타임아웃 10초가 설정되어 있다. 긴 작업을 시킬 때 다른 일을 하다가 끝났는지 계속 확인하는 것보다 알림을 받는 것이 생산성에 좋으며, 슬랙이나 구글 챗과 연동할 수도 있다는 것이다.

JSON 구조는 이벤트 타입(언제 실행할지), 매처(어떤 상황에 매칭할지), hooks 배열(실행할 훅 목록), type(훅의 종류), command(실제 실행할 셸 명령어)로 되어 있다.

이벤트 전체 흐름은 PreToolUse → 도구 실행 → PostToolUse → Notification → Stop 순서다. PreToolUse는 도구 호출 직전에 트리거되어 입력값을 검증하거나 승인·차단·수정이 가능하다. PostToolUse는 도구 실행 직후로 결과 검증이나 린트·포맷 같은 후처리에 적합하다. Notification은 사용자 응답 대기 시 알림 전송이나 로깅, 외부 서비스 연동에 쓰인다. Stop은 에이전트가 턴을 종료했을 때 최종 정리나 보고서 생성, 상태 저장에 쓰인다.

주의할 점은 훅이 실행되는 동안 클로드가 멈춰서 기다린다는 것이다. 훅이 끝나야 다음 작업을 진행하므로 시간이 오래 걸리는 작업을 넣으면 전체가 느려질 수 있다. 타임아웃을 꼭 설정하고 무거운 작업은 백그라운드로 돌리라고 권한다.

고급 팁 - 멀티 인스턴스와 워크트리

파워 유저의 고급 팁으로 멀티 인스턴스 운영을 꼽는다. 터미널 탭 여러 개를 열고 각 탭에서 다른 클로드 인스턴스를 돌리며, 탭 이름을 바꿔두면 어떤 탭이 뭘 하는지 한눈에 보인다. 인증 작업, 버그 픽스, 리팩터 식으로 나누는 것이다. 독립적인 기능을 개발할 때나 버그 수정과 기능 개발을 병행할 때 좋지만 인스턴스가 많을수록 API 사용량이 증가하니 리소스 관리에 주의하라고 한다. 실제 iTerm 화면에서 네 개 인스턴스에 프론트엔드, 백엔드, 데이터베이스, 테스트로 이름과 색깔을 붙여둔 것을 보여준다.

여러 인스턴스가 같은 디렉토리에서 동시에 작업하면 같은 파일을 수정하며 충돌이 나고 작업이 꼬인다. 이를 해결하는 것이 깃 워크트리다. 하나의 깃 저장소에서 여러 개의 작업 디렉토리를 만드는 기능으로, 브랜치를 바꾸려면 체크아웃을 해야 하는데 워크트리를 쓰면 브랜치마다 별도 폴더가 생겨 체크아웃 없이 여러 브랜치를 동시에 열어놓고 작업할 수 있다. 핵심은 커밋 히스토리나 리모트 설정은 공유하면서 파일 시스템은 완전히 분리된다는 점이다. 수동으로는 명령어가 여러 개 필요한데 클로드에는 워크트리 기능이 내장되어 명령어 한 줄이면 된다.

고급 팁 - 음성 입력

클로드 코드에 최근 릴리즈된 내장 음성 입력 기능도 소개한다. 터미널에서 /voice를 입력하면 음성 입력 모드가 활성화되고, 스페이스바를 누르고 있는 동안 녹음되어 놓으면 자동으로 텍스트로 변환된다. 한국어를 포함해 20개 이상 언어를 지원한다.

시연에서 /voice로 활성화하고 config에서 언어를 코리안으로 바꾼 뒤 “이 프로젝트 구조 분석해서 알려줘”라고 말하니 잘 인식된다. 긴 프롬프트도 빠른 시간 내에 생각하는 대로 전달할 수 있는 장점이 있다는 것이다. 강의자의 회사에서는 말해서 AI와 코딩하는 것을 스탠더드로 운영하고 있으며, 사람들이 AI와 직접 대화하며 코딩하는 트렌드로 바뀌어 가고 있다고 전한다.

고급 팁 - 커스텀 MCP로 제미나이 교차 검증

MCP는 편하지만 도구 설명만으로 공간을 많이 차지하므로 배시 스크립트를 쓰는 것을 추천하기도 한다. “check-db 스크립트 실행해”라고 하면 MCP 연결 없이 바로 실행되고 컨텍스트도 절약된다. 다만 배시 스크립트는 실행하라고 말해야 돌아가는 반면 MCP 도구는 클로드가 작업 중 필요하다고 판단하면 알아서 호출한다는 것이 장점이다.

실전편에서 언급한 “다른 AI에게 비평받기”를 커스텀 MCP로 만든다. 플랜 모드에서 세운 계획을 제미나이 API에 보내 리뷰받고 결과를 클로드에게 돌려주는 MCP다. 프롬프트는 “제미나이 API를 사용하는 플랜 리뷰 MCP 서버를 만들어 줘. 플랜 텍스트를 받아서 구현 계획에 빠진 부분이나 리스크를 지적해 줘”다. 제미나이 API 키는 구글 AI 스튜디오에서 발급받아 MCP 서버 환경변수에 설정한다.

실제로 “이 코드베이스의 아키텍처 개선 알려주고 플랜해 줘”로 플랜을 받은 뒤 플랜 리뷰 MCP를 호출하니 제미나이가 리뷰하고 그 피드백이 반영된 새 플랜이 나온다. 두 개의 AI 모델이 리뷰한 효과를 얻어 더 단단한 플랜이 나온다는 것이다.

/loop - 시간 기반 자동화

마지막으로 소개하는 것은 /loop와 스케줄 자동화다. 훅스가 이벤트 기반 자동화였다면 /loop는 시간 기반 자동화다. “/loop 5분 배포 상태 확인해 줘”라고 하면 한 줄로 5분마다 클로드가 알아서 배포 상태를 체크한다. 다른 슬래시 명령어와 조합도 되고 자연어로 일회성 리마인더도 걸 수 있다.

통합 데모 - 클라이언트 피드백 10개를 30분에

마지막은 스킬, 서브에이전트, 훅스, MCP를 하나의 실전 시나리오로 통합하는 데모다. 단순한 버그 하나 고치는 데모가 아니라, 실제로 작업 중이고 4월 런칭 예정인 개인 프로젝트를 클라이언트에게 보내 받은 1차 피드백 10개를 한 큐에 수정하는 과정이다.

프로젝트는 쿠팡 로켓그로스 정산 분석 앱의 대시보드로, Next.js·API·수파베이스 기반 모노레포 구조다. 피드백은 매출 수수료 매칭 버그, UI 텍스트 한국어 변경, 드롭다운 가시성 개선, 사이드바 메뉴 위치 이동 등 10개이며 수동으로 하면 반나절 정도 걸릴 분량이다.

1단계는 음성 입력이다. 긴 피드백을 음성으로 클로드에게 전달한다. 2단계로 플랜이 생성되면 앞서 만든 커스텀 MCP로 제미나이에게 플랜 리뷰를 받는다. 제미나이의 긍정적 평가와 주요 개선 제안 항목들이 나오고, 어떤 것을 반영할지 직접 결정한다. 그다음 플랜을 plan.md 파일에 넣어 참조하게 한다.

3단계는 서브에이전트 병렬 실행이다. 미리 만들어둔 백엔드 엔지니어, Next.js 프론트엔드, 유닛 테스트 제너레이터 세 에이전트를 병렬로 돌린다. 프론트엔드와 백엔드는 독립적이니 동시에 돌릴 수 있고 테스트도 마찬가지인데, 서로 독립성이 확보됐을 때만 병렬 실행할 수 있다고 강조한다. 백엔드는 파란색, 프론트엔드는 빨간색으로 표시되며 진행된다.

작업이 완료되자 앞서 만든 Stop 훅이 트리거되어 알림이 온다. 커피를 마시며 다른 작업을 하다가 알림으로 완료를 알고 돌아올 수 있었다는 것이다. 병렬로 프론트엔드·백엔드·테스트가 모두 5～10분 정도에 끝났다.

4단계는 코드 리뷰다. 코드 작성은 끝났지만 코드 리뷰는 꼭 해야 하며 가장 중요하다고 강조한다. 클로드 코드에 이미 코드 리뷰 플러그인이 있는데, 이를 쓰려면 PR을 생성해야 한다. PR을 생성하니 코드 리뷰 스킬이 로드되고, 그 플러그인 안에서도 다섯 개의 리뷰 에이전트를 병렬 실행하는 것을 볼 수 있다. 에이전트를 병렬 실행하는 것은 통상적으로 쓰이는 커먼한 패턴이니 모두 쓸 줄 알아야 한다는 뜻이라고 짚는다. 리뷰 결과 “근본적인 설계 충돌 버그의 가능성이 있다”는 지적이 나왔고, 리뷰를 하길 잘했다고 말한다.

5단계는 커스텀 스킬 client-report로 클라이언트 보고서를 자동 생성하는 것이다. “클라이언트 보고서 작성해 줘”라고 하니 브라우저에서 보고서가 열린다. 보고일과 변경 PR 번호, 진행 요약, 항목별 수정 내용까지 정리되어 있다.

정리하면 여덟 단계를 거쳤다. 음성 입력으로 복잡한 피드백 10개를 30초에 전달하고, 커스텀 MCP로 경쟁 모델이 플랜 품질을 검증하고, 서브에이전트 병렬 실행으로 프론트·백엔드·DB·테스트를 동시에 작업하고, 훅으로 작업 완료 시 알림을 받고, 코드 리뷰 에이전트가 전체 변경사항 품질을 검증하고, 커스텀 스킬로 클라이언트 보고서까지 자동 생성했다. 수동으로 반나절 걸렸을 10개 피드백이 클로드 코드 파이프라인으로는 코드 수정부터 클라이언트 보고서까지 30분 정도밖에 걸리지 않았다는 것이다. 이것이 진짜 1인 개발자의 풀 워크플로우라고 정리한다.

마무리 - 에이전틱 엔지니어

세 편의 시리즈를 한 줄로 정리한다. 입문편은 CLAUDE.md 세팅, 단축키, 필수 명령어 등 기본기, 실전편은 컨텍스트 관리와 워크플로우, 심화편은 스킬·서브에이전트·훅스·병렬 실행 같은 자동화다.

마지막 메시지는 이렇다. 이 시리즈에서 다룬 것들을 하나씩 적용하는 순간 더 이상 코드를 짜는 사람이 아니라 AI 에이전트를 설계하고 오케스트레이션하는 사람, 즉 에이전틱 엔지니어가 된다는 것이다. 스킬을 만들어 AI의 능력을 확장하고, 서브에이전트를 띄워 병렬로 처리하고, 훅으로 워크플로우를 자동화하는 것은 단순히 도구를 잘 쓰는 게 아니라 개발의 패러다임 자체를 바꾸는 일이라고 말한다. 1인 개발자가 팀급 생산성을 내는 시대이며, 지금 그 시작점에 서 있다는 말로 강의를 맺는다.
